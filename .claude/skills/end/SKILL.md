# end — 日次ループのセッション終了

停止時の作法。必ずこの順序で行う(`CLAUDE.md` §14.3)。

## 手順

1. **`NEXT_SESSION.md` を更新する**
   - 「3. 直近の作業ログ」にある既存の節を切り取り、`docs/archive/NEXT_SESSION_log.md` の「過去の作業ログ」節の先頭へそのまま移してから、今回の節を 1 件だけ置く(本書は常に直近 1 セッション分)。
   - 今回の節には、ユーザーの指示、実装内容、変更ファイル、検証結果(`tools/verify.mjs` の結果、E2E の有無、画面確認の有無)を具体的に書く。未完了/失敗なら、何が問題で次に何を試すべきかを明記する。
   - PR に言及する場合は記憶で書かず、GitHub の MCP ツールで現在の状態(open/merged/closed)を確認してから書く。
   - 「1. 現状サマリ」は次回に効く未解決の制約・懸念だけを目安 5 件以内に保ち、超過分・解消済みは `docs/archive/NEXT_SESSION_log.md` の「旧『1. 現状サマリ』バックログ」へ移す。「2. 次回の着手点」は目安 8,000B 以内に保ち、完了・解消済みの項目は同「旧『2. 次回の着手点』バックログ」へ移す。
2. **`docs/改修マスタープラン.md` の進捗表を更新する**
   - 完了したタスク行は `docs/archive/マスタープラン_完了タスク.md` の該当フェーズ節へ移し(状態セルは `✅ <日付> <完了内容の要点>`)、本体の表からは削除して「> **完了済み(N件)**: …」の ID 一覧と件数を更新する。
   - §2(全体進捗サマリ)も必要に応じて更新する。新たに見つかった作業はタスクとして起票する(ID は同フェーズの最大番号+1)。
3. **新しい教訓があれば記録する**
   - 全文は `rules/lessons_archive.md` の末尾に `### L<最大番号+1> <見出し>` + 空行 + 本文(**事象**/**原因**/**対処** の箇条書き)で追記する。
   - `rules/verification.md` の「教訓インデックス」の該当カテゴリに `- L<番号> <見出し>` の 1 行だけ足す(1 行 120 バイト以内、本文は書かない)。
   - 教訓とは非自明な事実・ハマりどころ・回避策であり、作業ログではない。既存と重複するなら追記しない。
4. **commit / push する**
   - `git status --short` で意図しないファイル(一時ファイル等)が混ざっていないか確認してからステージする(`git add -A` を使う前に一覧を見る)。コミットメッセージは日本語。
   - push 前に `git fetch origin` で origin が進んでいないか確認し、進んでいれば取り込む(競合したら自分で解決せず、競合ファイル一覧をユーザーへ報告して止まる。ドキュメントだけの追記競合で両側を残せば済む場合のみ解決してよい)。
   - 作業ブランチへの push は検証完了済み(verifier 全項目パス、またはコード変更なし)なら確認不要。**`main` への push・マージは常にユーザーの許可を得る**(`CLAUDE.md` §14.5)。
5. **セッション継続 vs `/clear` を一言提案する**: 次のタスクが今回と同じファイル・設計の続きで、会話にしか無い確定事項が残っているなら「続行推奨」。次のタスクが無関係の別領域、確定事項が書き出し済み、大きなツール出力が文脈に残っている場合は「`/clear` 推奨」。提案に留める。

## 注意

- 終了条件(連続 3 回失敗・ターン 30)で停止する場合も、新規タスクには着手せずこの手順のみを行う。
- 削除を伴う操作は都度リスクを説明して確認を得る。分類器にブロックされた操作はサブエージェント経由で回避しない。
